Capacity today, by GPU type

Valid configured capacity versus what is actually running. Dead config is excluded: 8 of the 10 capacity reservations named in main.tf no longer exist in EC2, and terraform keeps their ASGs alive so they advertise instance counts that can never be filled — 112 GPUs' worth. What remains is 2 live reservations (4 H100 + 2 B200 nodes) plus on-demand asks. The remaining gap is real capacity AWS is not currently filling.

GPU-hours consumed per month, by GPU type

Reserved GPU-time actually served (pod scheduled on a node). Demand has been broadly flat at 12–16k GPU-hours/month since April, but it has migrated almost entirely onto h100 and b200 as the older h200 and a100 pools disappeared.

Utilization of the GPUs that exist

Share of available GPU-time that was reserved, for the two pools that carry the load. Both roughly doubled since January — not because demand grew, but because the fleet shrank underneath it. Fleet-wide the number is far lower (25% in July) because the small pools sit almost entirely idle: RTX PRO 6000, T4, L4, A10G and A100 together hold 36 GPUs and drew under 1% of July's GPU-hours.

Active users per month

Distinct GitHub users who had at least one reservation running that month. Peak was 38 in March; the trend since is gently down while GPU-hours per user has risen.

Estimated monthly cost

On-demand nodes are billed actuals (Cost Explorer, attributed by the aws:autoscaling:groupName tag; list rates reproduce them to the dollar). H100/B200/H200 run in prepaid Capacity Blocks charged upfront in a single month, so they are amortized: each month is priced from the node-hours gpu-dev actually ran that month. The quantity is measured, only the rate is uncertain — bars use the blended rate the account really paid. Hover a bar or open the table for the on-demand-list upper bound; it runs about 4× higher and is plotted nowhere because it would flatten everything else.

How these numbers are derived

  • GPU-hours = gpu_count × (end − launched_at), clipped to each month. end = reservation_ended → cancelled_at → expired_at → failed_at → expires_at → now (for active). Records with no launched_at (1,059 — queued or failed before a pod was scheduled) are excluded; every record that has launched_at also has a node assigned, so this counts real allocated GPU-time.
  • Utilization denominator is measured delivered capacity: the node-hours each ASG actually ran that month (Cost Explorer usage quantity, attributed by the aws:autoscaling:groupName tag) × GPUs per node. Instance-hours are recorded even for capacity-block pools whose cost shows as $0, which is what makes this measurable. It validates against live data — July measures 32 h100 and 16 b200 GPUs versus 30 and 14 delivered today. Where the observed high-water mark of concurrent allocation exceeds the ASG-measured figure, the high-water mark is used instead, since that means pods ran on nodes outside the ASGs: the one real case is h100 in March (99 GPUs concurrent vs 30 ASG-managed), the non-ASG “pet” H100 nodes from the 2026-03-09 incident.
  • Dead capacity reservations are excluded. Each CR id in the prod capacity_reservations block was checked against EC2: 8 of 10 no longer exist, so their ASGs advertise 112 GPUs that can never be filled. Removing them takes configured capacity from 244 to 132 valid GPUs, of which 80 are running (61%). Entries with id = null are plain on-demand — a legitimate ask with no reservation guarantee — and are counted as valid.
  • No historical configured-capacity series is shown. The 8 dead reservations are gone from the EC2 API, so their expiry dates are unrecoverable and there is no way to tell which months they were still valid in. Utilization is therefore reported only against measured delivered capacity, never against config.
  • MIG slices are converted to fractional physical GPUs (1g = 1/7, 2g = 2/7, 3g = 3/7) so they are not double-counted against their parent h100/b200 nodes.
  • CPU pools (20 always-on c7i/c7g nodes) carry no GPUs and are excluded from GPU math. They served 762 node-hours in July — roughly one node's worth of the twenty.
  • August is partial (1–7 Aug, 169.5 h). Its GPU-hours bar is therefore short by construction; its utilization rate is directly comparable.
  • Cost. On-demand pools are exact: Cost Explorer unblended spend, filtered to gpu-dev's own ASGs via the aws:autoscaling:groupName cost-allocation tag, and us-east-2 list rates reproduce those actuals to the dollar (no Savings Plans or Reserved Instances exist on this account). The H100 and B200 nodes run in prepaid Capacity Blocks: AWS charges those upfront (both were purchased in April) and does not tag them per-ASG, so their true price is not retrievable. The range given spans the account's blended effective rate for those instance types over Jan–Jul ($14.64/h for p5.48xlarge, $21.84/h for p6-b200.48xlarge) up to on-demand list ($55.04 and $113.93). For an exact figure, read the capacity-block purchase amounts off the April invoice.
  • Caveat: reservation records are the unit of measurement, so a held-but-idle GPU counts as used. This measures reservation utilization, not SM occupancy — for the latter, use the DCGM metrics in Grafana.
